harness-ai

Claude Code skills and a Python CLI that prepare a repository for AI coding agents, measure where it stands, and move it forward one step at a time. A second plugin, ai-sdlc, takes a ticket to production.

The prompt explains. The code checks. The pipeline executes.
2 plugins 16 shipped skills 1 internal skill 5 levels, from 0 to 4 2 CLIs on the Python standard library

The problem. An AI coding agent starts every session knowing nothing about your repository. It does not know the command your CI really runs, the folder that looks dead but is still used, the deployment it must never trigger. So it guesses, and you correct it, again and again.

The usual answer is a long instruction file. It does not hold: past a few dozen lines the agent skims it, nobody prunes it, and a rule written in a prompt is a wish, not a guarantee. An agent that "must not deploy" will deploy the day a ticket asks it to.

A harness is everything around the agent that makes its work reliable: a short AGENTS.md that says only what the agent cannot discover, rules enforced by tools rather than by sentences, a loop that turns review comments into rules, and pipelines that keep the privileged actions. harness-ai helps a team build one, one step at a time, seeing at each step what has progressed.

The "cut the agent" test

Cut L1 and L2. Do L3 and L4 still serve a human in a hurry? If yes, the agent is an accelerator. If not, some process has leaked into the prompts. This is why every skill of harness-ai stands on a CLI: the skill tells the order, the CLI guarantees.

The progression

Five levels, and the right to stop

Each level is earned by checks that harness status measures in the repository, never by a declaration. A level is a place where you can stay: you say which one you aim for with harness target, and beyond it the tool proposes nothing. Click a level.

The level measures the shape of the harness: files, sections, mentions. It does not say that the agents work better. That proof comes from the trend of signals from one harvest to the next, and from the bench on the sample projects.

What they share

Six habits every skill keeps

The map first

Before any question, the skill shows where the repository stands with harness status --map: where you are, where it is going, the plan. It updates the map at the end.

One question, once

Questions are asked together, each with its reason, its options, their cost and the proposed default. Never one at a time along the way.

The text explains, the CLI guarantees

What must hold lives in a program that refuses a result that does not: a finding that cites no line of the diff, a fact not quoted word for word, a command missing from the procedure.

One step, then stop

Each skill does one thing, reports with what is not verified, and stops. What comes next is another call, and you decide it.

What it never does

Each skill writes it down: review does not approve, ship does not tag, run does not touch production, qa disables no test.

Plain words

An internal code (S1, P1, stop_at) never reaches the user alone: it comes with what it means, in the language of the conversation.

What is established

Where the proof stands

Three states, always the same words, those of docs/capabilities.md. Click a name to find it on the map.

A measurement is one draw, not an average, and the test cases were written by the model being evaluated on them: they are easier than a real repository. The measurements of the ai-sdlc skills played their earlier French text; the English text that ships today has not been played yet.

To try it

Install, or measure without Claude Code

In Claude Code (the repository is private: your GitHub account needs access to it):

/plugin marketplace add jrechet/harness-ai
/plugin install harness-ai@harness-ai
/plugin install ai-sdlc@harness-ai

Without Claude Code, with Python 3.10 or later and nothing else to install:

python3 harness-ai/cli/harness.py status /path/to/your/repo --map

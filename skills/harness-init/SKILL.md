# Harness init — step 1

An AGENTS.md generated by scanning the repository (tree, build commands, naming conventions) is noise: the agent discovers all of that alone by reading the code. A command only deserves its line if it surprises: the one the repository lets you guess is not the one to run. Useful rules come from incidents, not from a scan. So this skill sets up **little**: a short file that says only what cannot be discovered, and an explicit mode.

It sets up level 1, "Framed", and nothing else. A level is a place where one can stay: what is written here must stand without the next step. No Maintaining section, no harvest marker, no Working process, no task contract: those are steps 2 and 4, which harness-step proposes when the user wants to go further. A file that cites a contract that does not exist yet promises what it does not keep.

Default mode: **delegation** (the agent receives a whole task and comes back with a PR). Assistance (the human drives and reviews every diff) is chosen explicitly in the interview.

## Guide the user

**Show the map first.** Before any action or question, run `python3 "${CLAUDE_PLUGIN_ROOT}/cli/harness.py" status --map --no-write <repo>` and show, in at most six short lines plus the map:
- **Goal**: give the agent a short instruction file with what it cannot find alone: how it works here, the rules, what it must never do.
- **Plan**: 1. four questions · 2. read the repository · 3. write the file · 4. measure · 5. report.
- **Where we are**: the map ("you are here"), and whether instruction files already exist.
- **Where we are going**: level 1, Framed: the agent knows the project, its rules and what it must never do. Nothing beyond.
- **Now**: the four questions, asked together.

**Offer the page.** With the map, write the picture of it: `python3 "${CLAUDE_PLUGIN_ROOT}/cli/harness.py" status --no-write --page <repo>/.harness/state.html <repo>`, and give its path: one file to open in a browser, showing the files present or missing layer by layer and the steps to the target, one by one. Write it again at the end, so the user sees what moved. Never write that page yourself: it only shows what the command measured.

**Ask with context.** For each question, say why it is asked and what the answer changes in the file; give the proposed default and what happens if the user takes it. One decision per question.

**Plain words.** No check ids, no signal codes, no undefined internal word in what the user reads ("guardrail": a test or CI check that enforces a rule). Speak the language of the conversation. **The files you write follow the repository's language**: an English repository gets the English template; a repository whose docs and comments are in French gets the same sections in French (`Mode : **délégation**`, `## Règles`, `## Interdits`, `Pourquoi :`, `Vérifiée par :`, `(non vérifiée)`): `harness status` reads both.

## Steps

### 1. Interview — four questions, at once
Ask them together, each with why and the proposed default. Start nothing before the answers.

1. **Mode** — why: it decides who checks the agent's work, and how strict the rules must be. Delegation (default: the agent takes a whole task and opens a PR) or assistance (a person drives and reviews each change)? If the team reviews every diff live and no agent runs outside a session, propose assistance.
2. **Forbidden** — why: these become the lines the agent never crosses. What must an agent never touch or do (folders, secrets, shared database, production migrations, force push)?
3. **Tools and CI** — why: it decides which stub files to write and which rules are already enforced. Which agents (Claude Code alone, or also Copilot, Cursor, Codex)? Which CI, and which checks **block** merging today?
4. **What is written nowhere** — why: it is the only answer reading the repository cannot replace. What do you repeat at every review, or what does a newcomer learn by getting it wrong, that no file says? A fact filed in an ADR or a post-mortem, the agent finds alone; this one, never. It is worth a rule, with "said by the team" as its why. If the answer is "nothing", write so in the report; do not invent one.

If the owner does not know ("I never read it again"), do not fill in for them: write less. The team, the first task to delegate and the working process are not asked here.

### 2. Look at the repository — write nothing before checking
- **Where the facts are.** ADRs, post-mortems, operations notes, CONTRIBUTING, session notes left by an agent: that is where dated incidents live. Read them before the code. One quantified incident is worth ten conventions.
- **Existing instruction files** (`AGENTS.md`, `CLAUDE.md`, `.cursor/rules`, `copilot-instructions.md`): never overwrite. Sort each line: keep, shorten because a guardrail carries it, remove. A removal has a reason, see "Removing".
- **The right branch and folder files.** Read the instruction files on the branch the PR will target. Look for `CLAUDE.md` and `AGENTS.md` in subfolders (`find . -name CLAUDE.md -o -name AGENTS.md`): they are loaded on demand, and that is where what concerns only them goes. They are cleaned like the root one.
- **Secrets.** Look for API keys, passwords, tokens (`grep -rnE "apiKey=|api_key|token|password|secret|Bearer |sk_"` on the instruction files, the config and what they include). A secret found is never copied: say in the report where it is, that it stays in git history and must be regenerated, and add the matching Forbidden line.
- **Real commands**: find build, test, lint, and **run them**. A command that fails or does not exist does not go in the file; it goes under "not confirmed" in the report.
- **Commands that surprise.** `python3 "${CLAUDE_PLUGIN_ROOT}/cli/harness.py" commands <repo>` compares what the CI runs with what the ecosystem lets you guess: a wrapper (`make it` where you would expect `mvn verify`), options that change what runs, a target the CI does not run. Each unwritten candidate is confirmed: first read what it runs (the Makefile target, the script), run it only if it only checks, then it goes into the "what changes → what to run" table, with the obvious command it replaces if they are not equivalent ("`make it`, not `mvn verify`"). A delivery candidate, or any command that pushes, publishes or writes outside the repository even if the tool did not see it as such, is never run: it is a question for the owner, for a Forbidden line. An obvious command the CI runs as is needs no line.
- **Guardrails, and whether they block.** For each linter, architecture test, check script: note its path, what it checks, and read the CI to see whether it **blocks**. A job in `continue-on-error`, a path filter that does not trigger it, a local hook, a job cited by a document but absent from the workflow: this guardrail guarantees nothing. Tests that assert nothing either.

Test for each candidate sentence: *if I remove it, does the agent do anything differently?* If not, it does not go in the file. A rule that a check enforces passes this test: without its line, the agent only meets the rule when the CI turns red.

### 3. Writing
From `references/agents-template.md`, block "Step 1":
- `AGENTS.md` at the root, **under 60 lines**, mode line at the top. Empty sections are removed rather than filled with generic text.
- Each rule, and each forbidden item, carries three things: **why** (the incident, or "no known incident" rather than an invented reason), **what enforces it** (`Enforced by: <path>` only for a guardrail you saw block, otherwise `(unverified)`), and **since when** (`[YYYY-MM]`, the date of the incident or decision; failing that, today). A rule taken from an old file keeps its original date: it does not get younger because it is copied.
- A rule the repository already breaks says so, with the file: the agent must not take the counter-example as a model.
- Stubs: `CLAUDE.md` containing only `@AGENTS.md`; `.github/copilot-instructions.md` and `.cursor/rules/agents.mdc` according to the declared tools.
- A harvest marker already present is kept as is. None is added.

### 4. Gate — the measured state
`python3 "${CLAUDE_PLUGIN_ROOT}/cli/harness.py" status <repo>` writes `.harness/state.json`. Expected: level 1, five checks out of five, no "reference without a target". Fix before handing back. The full audit is not the gate of step 1: it is a level 3 step.

### 5. Report, then stop
Always the same format:
- **The map, updated**: the output of `status --map`, then one line: what this run did, where the repository is now.
- **Before and after**: level, lines loaded per session, number of rules.
- **Files** created or modified (path, lines).
- **Removed**, by reason, one line each with the reason.
- **Secrets** found and what remains to do.
- **Rules written**, with their status (enforced by what, or unverified) and their date.
- **Commands** confirmed and not confirmed, and the `harness commands` candidates you did not keep, with the reason.
- **Questions** for the owner, numbered, each with why and the proposed default: stale lines to confirm, what you observed without being able to explain it.
- **What comes next**, in plain words and without doing it: level 1 is a place where one can stay (in assistance, often enough); level 2 would bring "review remarks become rules" and asks for a review habit and a few weeks. The user decides (`harness target`), and harness-step leads it.

## Removing

On a repository that already has instructions, most of the work is removing. The question for each line is not "is it true" but "does it still change what the agent does". Three reasons, not to be confused:

| Reason | It is | Examples | What we do |
|---|---|---|---|
| **Useless** | Discoverable in the repository, or what a model does without being told | Tree, stack, "write clean code", "think step by step", session log | Remove, without asking |
| **Harmful** | Written for a limit that is gone, or contrary to a guardrail: it degrades the work of today's agent | "Rewrite the whole file beyond 500 lines", "ask for confirmation before every command" in delegation, an instruction the CI rejects | Remove, and report it separately |
| **Outdated** | True yesterday, not today | Compatibility with an abandoned browser or version | **Ask**: only the owner knows. An outdated line is removed after the answer, never before |

Never remove a line born of an incident because it looks obvious: it is precisely the one the repository does not say. In a generated file of a hundred lines, there are often two, at the very bottom.

## Delegation vs assistance — what changes at step 1

| | Delegation (default) | Assistance |
|---|---|---|
| Who checks | The CI and the guardrails; nobody reviews along the way | The human, at every diff |
| `(unverified)` rule | A debt: it will be skipped one day in ten | A context cost only |
| Natural next | Guardrails (level 3), then process and contracts (level 4) | Often nothing: level 1 is enough |

## What is not written
- Tree, module list, tech stack: discoverable.
- Conventions the model already applies (standard naming, idiomatic resource handling).
- Untested commands, "just in case" rules, generic principles.
- "Enforced by" for a guardrail not seen blocking.
- The material of the next levels.

## Common pitfalls
- Answering the interview questions yourself to go faster: the mode and the forbidden items come from the user, not from the scan.
- Asking the four questions before showing where the repository stands and why each question matters.
- Overwriting an existing CLAUDE.md because it is bad: sort line by line and say what was removed.
- Going over 60 lines "because it matters": if it matters and is long, it is a reference file loaded on demand.
- Forgetting the mode line: harness-audit uses it to choose its scoring.
- Believing a document that says "enforced by the lint" without opening the workflow.
- Chaining into the next step because you are there: the user asked for nothing more.

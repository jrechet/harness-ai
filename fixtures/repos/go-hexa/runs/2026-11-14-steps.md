## What was blocking
Level 2 is only won with real reviews: a `rule:` in a comment, a harvest that finds it. The skill always took the first level not reached, and `status` only proposed its actions. Targeting level 3 therefore meant waiting weeks before laying a guardrail that can be written today: exactly the blocking that C3 forbids.

The fix, in the CLI and in the skill: `status` marks as "waiting" what only time makes pass, and a level that is only waiting for that does not hold back the next targeted level. The level reached, for its part, does not change: the signal is still needed to count level 2.

## The guardrail written at level 3
A Go test that walks every write route and requires `Idempotency-Key`, with a list of exemptions in which each entry gives its reason, and a second test that fails if an exemption no longer matches any route. The agent saw it bite on a fake route, then removed it. The rule now carries "Enforced by" and says what the test does not cover: the key lookup inside the transaction is left to the review. Verified here: the test passes, and goes red on a write route added without a key.

One defect: a badly formatted line of `server.go`, which `gofmt -l` reports. The job that would see it is `lint`, which does not block.

## The second guardrail
`tools/migrationcheck` compares `migrations/` with the base branch and fails if an existing file changes; a new `migrations` job of the CI runs it on every PR, without `continue-on-error`. Verified here: an added migration passes, a modified applied migration fails with the expected message. The migrations rule and the matching forbidden item carry "Enforced by". The checks of level 3 all pass except the audit, which will be the next step; the level reached stays 1, level 2 is waiting for its review signal.

## The audit as a step of level 3
`harness-step` ran `harness-audit` and filed its JSON in `.harness/audit.json`. The audit finds a legitimate P1: `make reset-db` and `make migrate` check that a `DATABASE_URL` is given, not that it is local, whereas the forbidden item comes from a lost acceptance database. The check "audit with no open P1" therefore stays red, as `steps.md` plans: handling the P1 is the next step. The report says so.

The grader counts a problem, "no check flipped". The session's reading: it is the grader that is wrong, an audit that appears is the step `steps.md` describes. The fix of the grader was written then withdrawn without being pushed: changing the grader after seeing a run is forbidden, and the session's guardrail refused it. It is waiting for the owner; the score stays the original one.

## The P1 handled
`tools/localdb` refuses any `DATABASE_URL` whose host is not local, called at the head of `make reset-db` and `make migrate`, with its test. Verified here: `staging.internal` is refused with a message that points to the operations note, `localhost` passes, the tests are green. The agent marked the P1 resolved in `.harness/audit.json` after the fix, without rerunning the audit. The four checks of level 3 pass; the level reached stays 1, level 2 is waiting for its signal.

## The grader, fixed after the fact
The grader required a check to flip. Yet the skill guards **one** rule per step, and `L3.guarded` only flips at half of the rules. It now also counts a rising share of guarded or justified rules. Fixed after seeing the run: I say so. The opposite case is tested, and the "before" step, which does nothing, stays a problem.
